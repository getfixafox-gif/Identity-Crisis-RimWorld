# v0.3: контракт ядра преобразования (B → C/D)

База: `beta/v0.2`, `14aacd9c0b2ff7e1fba2e7b781a0c740caab1c7d`.
Статус: реализация без сборки и тестирования, draft. Проверка только чтением исходников. Совместимость с конкретными версиями HAR и наборами рас не подтверждена.

## Публичный API

```csharp
public static TransformationPlan RaceSwapper.BuildPlan(Pawn pawn, AssimilationConfig config);
public static TransformationResult RaceSwapper.ApplyPlan(Pawn pawn, TransformationPlan plan, IntVec3 dropCell, Map map);
public static AssimilationReport RaceSwapper.Transform(Pawn pawn, AssimilationConfig config, IntVec3 dropCell, Map map);
```

`TransformationPlan`: public get-only `bool CanApply`, `string Error`, `AssimilationConfig ResolvedConfig`.
`TransformationResult`: public get-only `bool Success`, `bool Partial`, `string Error`, `AssimilationReport Report`.
Имена, возвращаемые типы и сигнатуры согласованного контракта сохранены. Это свойства, а не изменяемые поля.

`ResolvedConfig` каждый раз возвращает отдельную копию, включая `addonVariants`. Изменение этой копии или исходного config не меняет план. План привязан к конкретной пешке и исходной расе. После начала применения он одноразовый, даже если результат частичный.

## Подготовка, предпросмотр и сохранение

1. Вызвать `BuildPlan` с реальной пешкой; допускается заспавненная пешка для предпросмотра.
2. При `CanApply == false` показать отказ; не начинать операцию и не списывать ресурсы. `Error` — техническая диагностическая строка на английском, не готовая локализованная строка интерфейса. UI должен использовать локализованное общее сообщение и выводить подробности отдельно.
3. Использовать `ResolvedConfig` для предпросмотра. Тело, голова, волосы, борода, возраст, пол, основные цвета и индексы аддонов в нём разрешены и зафиксированы. Не вызывать повторно генераторы причёсок/аддонов в предпросмотре.
4. Хранить план в памяти и передать тот же объект в `ApplyPlan`, пока пешка находится внутри капсулы и не заспавнена. План не реализует `IExposable`.
5. Для сохранения игры можно сохранить копию `ResolvedConfig` существующим сериализатором `AssimilationConfig`. После загрузки построить план заново из **этой разрешённой копии**, а не из первоначальных авто-настроек. При изменившихся ограничениях новый план может отказать; молча менять выбор нельзя.

Случайный выбор разрешается только при подготовке незаданных значений. Применение не вызывает повторный выбор значений config. Низкоуровневые варианты текстур головы/тела, маски, декоративные цветовые каналы и другие внутренние генераторы HAR вне полей `AssimilationConfig` не являются частью гарантии совпадения портрета; их кэши могут регенерироваться HAR. Полное пиксельное совпадение не обещается.

**Ограничение автоматических цветов:** вместо незафиксированного генератора новой расы используются текущие видимые цвета пешки, превращённые в явные overrides. Это намеренное ограничение данной реализации; UI не должен подписывать их «случайный цвет новой расы». Если требуется именно цветовая палитра новой расы, нужна отдельная интеграция с генератором HAR. Палитры и ограничения всех сторонних рас не подтверждены.

## Preflight и безопасные отказы

До изменений здоровья, генов, `pawn.def`, одежды или компонентов выполняются проверки:

- живая человекоподобная пешка и полноценное целевое тело;
- наличие обязательных трекеров, допустимый конечный возраст/пол;
- строгие списки тела/головы HAR, ограничения стиля и пола; генозависимые головы не поддерживаются;
- доступность точных сигнатур ограничений HAR, включая endogene/xenogene при Biotech;
- известный результат проверок для всех текущих генов, одежды и оружия;
- совместимость компонентов и возможность безопасного переноса/извлечения имплантов;
- наличие используемых членов HAR для записи внешности.

`ApplyPlan` повторяет проверки изменяемого состояния перед мутациями и дополнительно требует незаспавненную пешку. Если есть экипировка либо извлекаемые импланты, нужны действительная карта и клетка выдачи. Карта не может быть частью `BuildPlan`, поскольку её нет в согласованной сигнатуре.

**ThingComp — консервативный режим:** набор живых компонентов должен в точности соответствовать целевым `CompProperties` по классу, количеству и ссылочной идентичности props. Создание, удаление, `Initialize` и перепривязка неизвестных компонентов не выполняются. Одного совпадения классов недостаточно. Это может отклонять большинство межрасовых переходов, включая переход Human ↔ HAR и переходы между HAR-расами с разными объектами props. Это ограничение безопасности, а не подтверждённая поддержка всех HAR-рас. Для расширения нужен отдельно реализованный и проверенный lifecycle, не обход проверки.

Имплант переносится только при однозначном customLabel либо при одинаковом количестве однотипных частей и существующем порядковом соответствии. Старый fallback на первую часть удалён. При отсутствии соответствия требуется предмет извлечения; иначе отказ до мутаций. Размещение извлечённого предмета и перенос снаряжения проверяют фактический результат. При неудаче выдачи снаряжения выполняется локальная попытка вернуть его в исходный трекер; это не полный rollback.

## HAR: разрешение не равно недоступности

```csharp
public enum HarRestrictionResult { Unavailable, Allowed, Denied }
HarCompat.CheckCanWear(ThingDef apparel, ThingDef race)
HarCompat.CheckCanEquip(ThingDef weapon, ThingDef race)
HarCompat.CheckCanHaveGene(GeneDef gene, ThingDef race, bool xenogene = false)
```

Отсутствующий метод, неверный тип результата или исключение дают `Unavailable`. Ядро отклоняет такую операцию до мутаций, если проблема обнаружена на preflight. Если совместимость ломается уже при применении, результат частичный, а не ложный успех. Старые bool-методы сохранены, но теперь возвращают true **только** для `Allowed`; fallback «ошибка значит можно» удалён. UI-хелперы best-effort остаются отдельными от строгого пути ядра.

## Обработка результата в капсуле (D)

- `Success=true, Partial=false`: только здесь применять последствия обращения, выдавать успешное письмо и запись журнала, завершать успешный процесс.
- `Success=false, Partial=false`: отказ до мутаций; ресурсы и успешные последствия не применять. При необходимости можно подготовить новый план после устранения причины.
- `Success=false, Partial=true`: выполнение началось и могло изменить пешку/предметы. Не показывать успешное завершение, не повторять автоматически, не вызывать `Transform` повторно. Сохранить пешку и диагностическое сообщение для явного восстановления владельцем. Частичный `Report` — диагностический, не отчёт об успешной ассимиляции.

Wrapper `Transform` возвращает `Report` только при `Success`; при любом отказе или частичном выполнении возвращает null и пишет ошибку в лог. Старый вызывающий код, который принимает null как успех, необходимо исправить в ветке D.

Полный rollback **не реализован и не обещается**. Исключение после начала мутаций останавливает следующие этапы; опасные ошибки не скрываются общим catch-and-continue. Карта и наличие клетки не гарантируют свободное место, поэтому выдача предметов всё равно может завершиться частично.

## Зависимости и оставшаяся интеграция

Ветка автономна от будущих настроек A. Никаких ссылок на новые поля `IdentityCrisisMod.Settings` не добавлено. Переключатели `allowRejuvenation`, `allowRegrowBodyParts`, `allowCureDiseases` и множители пока **не подключены**: ядро сохраняет базовую политику выбранного возраста и здорового нового тела. Их включение требует отдельного согласованного изменения preflight/плана и подготовки хедиффов; для запрета восстановления частей или лечения болезней недостаточно просто пропустить удаление хедиффов при смене BodyDef.

Не менялись `AssimilationConfig.cs`, `IdentityCrisisMod.cs`, капсула, UI, графика, основные ветки и чужие ветки. CHANGELOG не изменён из-за выданного ограничения набора файлов; запись для общего v0.3 следует добавить при интеграции.

## Проверка

Выполнено только чтение исходных и изменённых файлов, а также чтение открытых исходников HAR и декомпилированных API RimWorld для уточнения контрактов. Это не подтверждение компилируемости или игровой корректности.
